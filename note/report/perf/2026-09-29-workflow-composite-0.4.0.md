# 0.4.0 工作流组合工具性能报告（基于 647 次真实调用记录的分析与真机量化）

日期：2026-09-29 ｜ 环境：Windows 11 宿主 + VMware Workstation（RHEL-10 实测 VM）+ ZCode 真实会话数据库

## 1. 动机：历史会话数据指出的真瓶颈

从 ZCode 本地库（`~/.zcode/cli/db/db.sqlite`）提取 09-22 → 09-29 全部 vmware-mcp 调用（**647 次 / 23 个会话**）做量化分析，结论：单次调用延迟已不是瓶颈（最重会话纯工具等待仅占会话时长 6%），摩擦在**往返圈数**：

| 证据 | 数字 |
| --- | --- |
| 「上传→执行→回拷」三连圈 | 68 个完整圈（copy_to→run/script→copy_from），每圈 3 次调用 / 3 个模型回合 |
| stdout 通道闲置 | 124 次执行调用中 106 次输出 ≤50B（VIX 不回收程序 stdout，结果被迫写文件再回拷） |
| 最高频工具 | vmrun_copy_from 140 次，多数仅为取回小文本后本地 Read |
| 0.2.0 交付的目录拷贝 | 至今 0 次调用（描述无触发条件，模型默认逐文件） |
| 长任务等待 | power_query 等轮询循环（如 ×4 连呼等待开机）、后台作业产物反复 file_exists |
| 旧时代超时 | 58 次 30s 超时全部集中在 0.1.0 时代（09-22/23），0.2.0 后仅 3 次且为真实长脚本 |

模型回合经济学：最重会话 328 次模型请求累计 55.4M input tokens（99% cache-read），**平均每回合重读 ~169k token 上下文**。每消除一个中间回合即省一次该量级的重读与 10–25s 级延迟。

## 2. 交付（对应分析结论 ①②③④⑤）

| 工具 | 合并的旧形态 | 调用/回合变化 |
| --- | --- | --- |
| `vmrun_run_job` | copy_to + run + copy_from 三连 | 3→1 次调用，3→1 回合，直接返回 stdout + exit_code |

## 4. 真机验证抓出、单测抓不住的三个缺陷（均已修复）

1. **半成品窗口**：重定向文件在脚本启动时即被创建，wait_file 首探即中但内容未写完 → 改 `.part` 中转 + 完成后 `mv`/`move` 原子发布。
2. **exit 逃逸**：用户脚本 `exit 7` 会跳过 POSIX `{ }` 块外的收尾（退出码追加 + 发布）→ 改子 shell `( )` 包裹，`rc=$?` 走标记通道；cmd 用 `call :__vmjob` 子例程隔离。
3. **符号链接静默失败**：VIX 对 guest 内符号链接（如 /etc/os-release）报 OK 却不落宿主文件 → read_file 检测 OSError 并结构化指引 `run_job cat` 方案。

回归状态：单元测试 64/64，黄金快照 141/141 逐字节一致（含三新工具全成功路径）。

## 5. 预期收益测算（对照历史分布）

以最重历史会话（142 次 vmware 调用 / 68 圈三连）为参照：run_job 直接替换三连圈可省 **~136 个模型回合**（68 圈 × 2），read_file 覆盖高频小文本读取再省数十回合；按实测每回合 10–25s 的往返延迟计，单会话可压缩 **20–50 分钟**墙钟时间与等比例的上下文重读。工具侧 wall 基本持平（±25%），安全护栏（三层拦截/只读模式）、黄金快照等价性不受影响。

复跑基准：`benchmark/bench_workflow.py`（需 VMWARE_BENCH_VMX/USER/PASS 环境变量与运行中的 VM）。

## 6. 本轮不做

- REST-first（P2）：vmrest 凭据已可用，但改写调用家族属结构变更，留待独立版本评估。
- `vm_wait_power`（电源轮询折叠）：出现频次低（观察值 ×4 一例），暂以描述引导。
- 三家族工具合并：维持既有结论（破坏性大）。
